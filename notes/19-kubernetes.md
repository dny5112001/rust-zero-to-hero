# 19 · Running it on Kubernetes

> New to Kubernetes? Read [kubernetes-zero-to-hero](https://github.com/dny5112001/kubernetes-zero-to-hero) chapters 01–11 first.

This chapter explains **what** we run on Kubernetes and **why** each piece is
there. Chapter 20 shows how Terraform creates it all.

## What's in the cluster

```
your Mac :8070
   │  (kind port mapping)
   ▼
Traefik ingress (namespace traefik)          routes Host: api.localhost
   │
   ▼
Service notes-api  ──►  Pod notes-api  ×2     the Rust app (Deployment)
                              │
                              ▼
               Service postgres ──► Pod postgres-0  (StatefulSet + 1Gi disk)
```

All app objects are in the `notes` namespace.

| Object | Why |
|---|---|
| **Deployment** `notes-api` (2 replicas) | runs the app; replaces crashed Pods; rolling updates |
| **Service** `notes-api` | one stable address for both Pods |
| **Ingress** | sends `http://api.localhost:8070` to the Service |
| **Secret** `notes-api` | `DATABASE_URL` and `JWT_SECRET` (generated by Terraform) |
| **StatefulSet** `postgres` + PVC | the database, with a disk that survives restarts |
| **Secret** `postgres` | database user/password |
| **PodDisruptionBudget** | never take both app Pods down during node maintenance |

## How the Rust code and Kubernetes fit together

These are the details that make the app a **good Kubernetes citizen**:

### 1. Two health endpoints

```
readinessProbe → GET /health        checks the database. Failing = no traffic, no restart.
livenessProbe  → GET /health/live   process only. Failing = restart.
```

If the database goes down, Pods become **not ready** (no traffic) — but they're
**not restarted**, because restarting wouldn't fix the database. Your original
`/health` handler only needed one change: return **503** instead of 200 when the
database is down, so Kubernetes can tell.

### 2. Graceful shutdown, plus a short drain

When Kubernetes stops a Pod it sends **SIGTERM** and, at the same moment,
starts removing the Pod from the Service. The ingress takes a second or two to
notice. If the app stops instantly, requests already on their way **fail**.

We measured it: hammering `/health` during a rolling restart gave
**6 failures out of ~5,100 requests**. The fix in `main.rs`:

```rust
// after SIGTERM:
tokio::time::sleep(Duration::from_secs(delay)).await;   // SHUTDOWN_DELAY_SECONDS=5 in Kubernetes
// then axum's graceful shutdown finishes in-flight requests
```

After the fix: **0 failures out of 5,994**. (Many people use a `preStop: sleep`
hook for this; our distroless image has no `sleep` program, so the app does it itself.)

### 3. Zero-downtime rollouts

```hcl
rolling_update {
  max_unavailable = "0"   # never fewer Pods than wanted
  max_surge       = "1"   # start one new Pod, wait until Ready, then stop an old one
}
```

### 4. Migrations at start-up

Each Pod runs `sqlx::migrate!` when it starts. SQLx takes a database lock, so
two Pods starting together don't run the same migration twice.

### 5. Locked-down containers

`runAsNonRoot`, read-only root filesystem, all Linux capabilities dropped, no
service account token. The app writes nothing to disk, so this just works.

### 6. Resources

The Rust app needs very little: `requests: 50m CPU, 32Mi memory`, `limits: 128Mi`.

## Getting the image into kind

There's no registry: `kind load docker-image notes-api:<tag>` copies the image
into the cluster's nodes, and `image_pull_policy = "IfNotPresent"` stops
Kubernetes from trying to download it. On a real cluster you'd `docker push` to
a registry (ECR, GHCR) instead.

The tag is a **hash of the source code**, so every code change gets a new tag →
Kubernetes sees a new image → rolling update.

## Looking around

```bash
export KUBECONFIG=$PWD/deploy/terraform/01-cluster/kubeconfig
kubectl -n notes get pods,svc,ingress,pvc
kubectl -n notes logs deploy/notes-api -f
kubectl -n notes exec -it postgres-0 -- psql -U notes notes_db -c 'select count(*) from notes;'
kubectl -n notes delete pod postgres-0      # the data survives — try it
kubectl -n notes rollout restart deploy/notes-api
```

## Remember

- Readiness checks dependencies; liveness never does.
- Handle SIGTERM: drain briefly, then finish in-flight requests.
- `max_unavailable = 0` + readiness = zero-downtime releases.
